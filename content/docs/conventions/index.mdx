Conventions are decisions you only make once. Pick a name for a colour, a size for a gap, a prop for
a button variant, and write it down. After that, nobody chooses again. They look it up.

[The rules](/docs/principles/rules) say what a finished interface must do. This chapter says how to
build it so it stays that way: which tokens exist, what they are called, which numbers are allowed,
and how components expose their states.

decision has leaked out of the token layer.

## How to read MUST and SHOULD

The keywords follow [RFC 2119](https://www.rfc-editor.org/rfc/rfc2119), the same way the Vercel Web
Interface Guidelines use them.

- **MUST** means no exceptions without a written reason in the pull request.
- **SHOULD** means the default. Break it when you can say why in one sentence.
- **SHOULD NOT** means avoid it unless you can say why in one sentence.

## The six conventions that pay off first

If a project adopts nothing else, adopt these.

- **MUST** keep every colour, size, radius, shadow, duration and z-index in tokens. Pages use tokens only.
- **MUST** name tokens by role (`--color-text-soft`), not by value (`--grey-600`), anywhere a component reads them.
- **MUST** take spacing from the 4pt scale: 4, 8, 12, 16, 24, 32, 48, 64, 96.
- **MUST** use the named z-index layers. Never write `z-index: 9999`.
- **MUST** design and name every interactive state: default, hover, active, focus-visible, disabled, loading, error, empty.
- **MUST** check every page at 390px wide with no horizontal scroll.

## Why it works

A convention turns a taste argument into a lookup. Reviews get shorter because the question changes
from "does this look right?" to "is this the token?". New people, and AI agents, produce work that
matches on the first try, because the answer is written down instead of held in someone's head.
